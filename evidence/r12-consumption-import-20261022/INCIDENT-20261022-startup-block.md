# INCIDENT：R12 导入后 App 无法打开账本（2026-10-22）

## 结论

导入本身完整、数据一致；**App 冷启动被自身模型校验拦住**。现场已保留，未做任何修补。

## 现象

- 12 批导入全部成功，界面回执与 §3 锚点逐批一致，SQL 回读 `expenses=825 / expense_records=826 / import_batches=12 / 导入总额=100,450.11` 全部正确。
- 按 bundle id 退出后重新启动，首页显示「暂时打不开账本 / Stored facts or settings could not be used to calculate the monthly model.」，「重新打开」无效。
- 截图：`00-post-import-startup-error.png`；AX 文本：`10-startup-error-ax.txt`。

## 根因（已只读复现）

1. 源账单含 **14 行金额 0.00 的支出**：
   - 支付宝「其他」批（`r12-alipay-其他.csv`，锚点 91 行）13 行：医院/门诊「医保支付(不含自费)」；
   - 支付宝「购物」批（`r12-alipay-购物.csv`，锚点 108 行）1 行：「0 元付定」牙膏。
   这些是原始账单真实行，按任务书 §2「金额原样」保留，预览计为可导入，全部写入；对金额合计无影响（0.00）。
2. App 模型校验 `src/model/validation.ts` 对每条支出金额执行 `POSITIVE` 规则；首页取当月（2026-10-01～10-22）支出列表，其中命中 **3 行 0.00**（2026-10-11 两行医保、2026-10-18 一行 0 元付定），抛 `ModelValidationError: NON_POSITIVE_VALUE`。
3. 该错误被 `src/application/monthly-model-service.ts` 包装为 `ApplicationModelError`，即首页显示的报错。
4. 只读复现：把仓库同一份 `src/model` 源码编译到 `/tmp`，传入单条 `amount="0.00"` 的支出，稳定抛 `NON_POSITIVE_VALUE`。未改仓库、未改生产包。
5. 导入前库里没有 0 元支出，所以启动正常；这是「导入器接受 0 元、模型拒绝 0 元」的口径不一致，属应用缺陷，在本次真数导入下首次暴露。不是转换错误，也不是行数/金额锚点不符。

## 影响

- 当前（2026-10 内）App 首页不可用，无法回读「已花」= 100,513.11，也无法在界面查看债务/资产/现金。
- 数据库内容完整且一致；导入批次、镜像、哈希均可审计。
- 11 月 1 日后当月不再包含这些 0 元行，App 大概率能打开，但这只是绕过，缺陷仍在（以后再导入含 0 元流水会复现）。

## 未做的动作（遵守红线）

- 未删除/修改任何导入行（含 3 行 0 元）。
- 未 SQL 直插/直改，未动债务、收入、固定计划、现金/资产快照。
- 未改 `src/`、`src-tauri/`，未重建/替换生产包。
- 未动迁移备份、`.v8-quarantined` 与 terminal/receipt/permit 文件。
- App 保持报错页未再操作，供取证。

## 待户主/审核员裁决的恢复路径

| 方案 | 内容 | 代价/风险 |
|------|------|-----------|
| A（建议） | 出新任务书修应用口径：模型校验允许 0 元支出（或导入时把 0 元行按「非支出」处理/明确拒收），重建并验签新包后启动 | 需改代码+重建包，超出 R12 红线；周期最长，但修的是根因，且不动已导入真数 |
| B | 经户主明确授权，仅移除这 14 行 0 元导入行 | 违反「不删导入行/禁止 SQL 直插」；App 无删除入口，需专用可审计通道并过生产完整性门闸；会改动已验收锚点计数（824→810） |
| C | 等到 11-01 后启动 | 不改数据，但 10 月内无法用 App 回读；缺陷未修，未来导入再遇 0 元仍复现 |
| D | 回滚到导入前备份再重导 | **不可取**：现无 R12 前的库备份，现有备份是 R11 前/迁移前，会丢 R11/R11B 数据 |

建议：先按 A 立项修口径；若户主只要求马上能用，再单独裁决 B，并同步修订 §3/§5 锚点（824→810、总额不变），不得把「删行」当成 R12 的正常收尾。
