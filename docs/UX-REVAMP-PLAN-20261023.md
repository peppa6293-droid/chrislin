# 小钱家 · 体验改版方案（2026-10-23，待户主下发）

来源：户主 2026-10-23 真实试用后的两批反馈，共 14 个问题，已在代码逐条核实根因。
定位：本文件是方案，不是执行指令。执行须由户主审定后下发任务书。

---

## 一、总诊断

App 的数据模型其实分了三本账：

| 账本 | 数据 | 变化频率 |
| --- | --- | --- |
| 固定支出账 | 必要支出（房租/基本饮食/水电通讯/保险/家庭责任…） | 几乎不变，一年改几次 |
| 债务还款账 | 月供、信用卡应还 | 每月固定 |
| 弹性消费账 | 日常流水（吃饭/出行/购物…） | 每天发生 |

但界面上这三本账暴露得极不均匀：固定支出埋在「我的 → 综合维护」大对话框里找不到，债务只能改余额不能记还款，于是「记一笔」成了万能筐，什么都往里塞，账就乱了。首页又把「长期结构缺口」和「本月消费」混在一张卡里，三个数字互相没有算术关系，还每月都负——提醒成了噪音。

**改版主线：把三本账的入口和语言分开，首页拆卡，记账有多邻国式反馈，数据可进可出。**

---

## 二、问题清单与方案（按优先级）

### P0 · 每天都会碰到的

**1. 首页「这个月」卡片口径混搭**
- 现状：一张卡上放了「还可以安排（收入−固定支出−月供）」「已花」「目标」三个数，三者无算术关系；结构缺口每月为负，提醒成噪音。
- 方案：拆成两张卡。
  - **结构卡（长期）**：收入 − 固定支出 − 月供 = 结构余量。只在改收入/固定支出/债务时变化，配一句话说明白「这是长期格局，不用每月盯」。
  - **本月消费卡（短期）**：已花 vs 目标，多邻国式动画进度条，超支才提示。
  - 提醒只在「可行动」时出现（本月超支、还款日临近、逾期），结构性长期缺口不再每月重复刷屏。

**2. 记账没有反馈感、界面枯燥**
- 现状：保存 = 关弹窗 + 一行小字「已保存并重新读取确认，本月已花…」。无动画、无庆祝、无连击。
- 方案：多邻国量级的反馈层。
  - 记完一笔：庆祝动画（弹跳/粒子/进度条增长），不是弹一行字。
  - 记完一天：「今天记完了」的完成感（可带连击天数）。
  - 记完一月：月度小结庆祝页（PPT 式图文，不是数字表）。
  - 项目里 `DuoGuide`（连击/奖励）、`PixelWorld`/`SaveFeedback`（像素庆祝）是从未接线的死代码，**可参考交互逻辑，像素视觉不要搬**——像素风和多邻国圆润风不是一个体系。
- 同时全 App 换视觉语言：数字表 → 进度条/图形化表达（PPT 式图文优先），一屏一个问题，说人话。

**3. 日期控件又糙又啰嗦**
- 现状：原生 `datetime-local` 控件，标签写「日期和时间」，还要求精确到时间。
- 方案：只留日期（存储层本来只认业务日期，砍掉时间是安全的，已核实）；换成大尺寸日期选择器（日历式，不是大众表格里那种小输入框）。

**4. 两个入口跳到同一个页面（真 bug）**
- 现状：首页「稳住现金」和「建立余地」写的都是跳「安全垫情况」页，后者根本没有自己的页面。
- 方案：给「建立余地」建独立页面（储蓄/余地目标的图文进度页），并全量清查导航项是否还有复制粘贴错的路由。

**5. 数字排版粗糙**
- 现状：收支账本等处直接显示 9309.32、5325.93，无 ¥、无千分位。
- 方案：统一金额格式（¥ + 千分位 + 两位小数），全 App 一致。

### P1 · 账本分层（解决「乱」的根源）

**6. 固定支出找不到**
- 现状：功能其实存在（综合维护对话框里有「必要支出」维护），但入口在 我的 → 高级维护，日常路径根本找不到。
- 方案：把固定支出维护从综合维护大对话框中**抽出来独立成一个页面/入口**（首页结构卡旁即可直达），支持增删改必要支出项。综合维护对话框保留为高级入口。
- 该页面需含两个能力（户主 2026-10-23 确认，下月起就要用）：**① 维护**必要支出项；**② 记一笔实际支付**（如「这个月房租已转 ¥xxxx」），留下支付记录。支付记录只进固定支出账，不进弹性消费账，不重复计入模型（口径见第五节）。

**7. 债务没有还款功能（红线级）**
- 现状：债务页只能手改余额；「本月已计入还款」是模型计划值不是实还；页面大字是总负债、小字才是本月应还，数字主次颠倒。
- 方案：
  - 债务页增加 **「记一笔还款」**：选债务、填实还金额、日期 → 余额自动扣减 + 留下还款流水（历史可查）。
  - 页面排版反转：**本月要还（大字）**，总负债余额（小字参考）；「计划计入」与「实还」分开标注，不再混淆。
  - ⚠️ **红线**：还款涉及余额变动，必须遵守 V2/V1 双账本同步契约，两本账一起改、可对账；严禁直插 SQL 改库（生产库完整性门闸会拒启）；禁止改库凑数。任务书必须写清契约与回滚。

**8. 消费分类全显示「其他」**
- 现状：两个根因——① 导入整批共用一个分类；② V1 镜像把所有 V2 分类压平成「其他」，首页读的是压平后的数据。
- 方案：
  - 修镜像分类映射，让首页读到真实分类（涉及双账本读路径，需对账验证）。
  - 对已导入的 824 笔流水**按商户名/摘要做批量重新归类**，人工确认一次，不动原始账目内容。
  - 详见第 11 条导入智能化，二者可合并做。

### P2 · 数据可信、可迁移

**9. 消费记录不能删除/撤回（红线级）**
- 现状：记错没有任何挽回手段，全 App 无删除/撤回入口。
- 方案：
  - 流水列表每条支持 **删除 + 编辑**，删除前二次确认，可选「撤回」窗口（刚删的可恢复）。
  - ⚠️ **红线**：删除同样触碰双账本同步契约——删一条流水，两本账同步删除且可对账；实现与验收都以契约为准。

**10. 数据不能导出**
- 现状：无任何导出入口（页面自己写明「没有导入、导出或云同步入口」）。本地账本不能导出 = 换设备数据就没了。
- 方案：**全量导出**（JSON 全量备份 + CSV 流水表），一键下载到本地文件。导出内容含三本账全部数据，可作为迁移包。隐私页同步补说明。

**11. 账单导入是「麻烦用户」**
- 现状：仅支持支付宝/微信 CSV；整批只能指定一个默认分类和一个默认账户；用户要逐条核对列表再确认。
- 方案：按户主思路重做——**用户丢账单进来 → 自动分析归类 → 用户一键确认**。
  - 自动识别银行/平台账单格式（不止支付宝/微信，逐步覆盖常见银行 CSV/PDF）。
  - 分类自动匹配：按商户名/摘要做规则 + 本地智能归类，每笔给出建议分类和账户，置信度低的才标出来让用户看。
  - 确认界面一次通过（可批量改），不再一条条对。
  - 关于「开源 AI」：App 是本地优先，建议用**本地规则库 + 可选本地/开源模型**做归类，数据不出机器；模型只提建议，最终确认权在用户。具体选型（规则库先行 vs 引入本地小模型）可在任务书阶段由执行者评估后给出，不在本方案锁死。

**12. 收支账本不知道有什么用**
- 现状：首页底部折叠块「收支账本 = 财务概览」，把同样的数字换排版再放一遍，与主页重复。
- 方案：与首页卡片合并去重——有价值的内容（趋势、资产债务）并入主页信息架构，纯重复的删掉或改名收进二级页。保留必需的资产/债务名称占位不丢。

### P3 · 打磨

**13. 详情页太专业、像念论文**
- 现状：安全垫页 13 行标签+数字，「想知道怎么算」点开是计算说明文；一个「?」提示解决不了看不懂。
- 方案：图文化重做——每页回答**一个**问题（「安全垫够不够？」「这个月要还多少？」），进度条表达目标 vs 现状，结论先行、算法说明收进可展开层。语言全换大白话。

**14. 数据与隐私页太简陋**
- 现状：只有几段说明文字，且自述没有导出功能。
- 方案：随第 10 条导出功能一起充实：数据存在哪、怎么备份迁移、导出格式说明、隐私承诺（本地存储、无上传）。

## 三、红线汇总（执行任务书必须体现）

1. **双账本同步契约**：债务还款（第 7 条）、删除/编辑（第 9 条）、分类映射修复（第 8 条）都触碰 V2/V1 双账本，两本账必须同步变更且可对账，验收以契约为准。
2. **生产库完整性门闸**：数据只走应用界面，禁止直插 SQL 改库；禁止改库凑数。
3. **改代码重建须带热修授权段**（既有流程）。
4. **验收锚点分「当月/全量」两口径**（既有结论）。

## 四、建议执行顺序

1. 第一批（快、收益大）：P0 全部 5 项 —— 首页拆卡、反馈动画、日期控件、跳转 bug、金额格式。
2. 第二批（核心）：P1 的固定支出独立入口 + 债务还款功能（含双账本契约设计）。
3. 第三批（数据可信）：删除/编辑、导出、分类重建 + 导入智能化。
4. 第四批：详情页图文化、隐私页、收支账本去重。

每批独立验收，验收看「使用感受」而不是「功能有没有」——户主标准是不再觉得乱、有反馈感、看得懂。

## 五、口径已定（户主 2026-10-23 确认）

**结论：不存在重复计数。** 房租水电此前是银行转账给房东，没有做备注/记账，未进消费流水（只存在于交给项目组的账单里）。本月历史不做补录。

**下月起必须能记，功能板块必须有：**
- 固定支出账既要能**维护**（增删改必要支出项，见第 6 条），也要能**记一笔实际支付**（如「这个月房租已转」），留下支付记录。
- 口径：固定支出的维护和支付记录都发生在**固定支出账**，**不进弹性消费账**，模型不重复计入（首页结构卡的「固定支出」以固定支出账为准）。
- 这条并入第二批（P1 第 6 条）执行：固定支出独立页面 = 维护 + 月度支付记录两个能力，缺一不可。
