# 小钱家 iOS：协作分工 V2（取代 WORKFLOW-OWNER-VIEW 的岗位表）

日期：2026-10-30　状态：已由 Owner 口头确认（"C、保留"）。生效范围：M1 之后的所有任务。
**本文件给所有岗位读，不含模型名、价格、排名。** 模型到岗位的对应关系只由 Owner 掌握，不写进任何会发给执行 Agent 的文件（调度规则 V1.2 §10.5）。

## 1. 岗位

| 岗位 | 做什么 | 绝对不做 |
|---|---|---|
| **规划岗（PL）** | 拉方向；立项；写任务卡；拆任务；定口径的**提案**；维护未决问题清单；读复核与验收回执后调整计划 | 不复核自己出的任务卡；不替 Owner 做审美和命名决定；不直接批准自己的方案 |
| **执行岗（EX）** | 按任务卡做重复、范围清楚的工作；也可按任务卡写代码（包括财务、数据库、两本账，见第 3 节硬条件） | 不改任务卡范围外的文件；不定口径；不自称完成通过 |
| **复核岗（RV）** | 对**一张**已执行的任务卡做独立复核：读原始证据、重跑门禁、对照验收标准 | 不改代码；不复核自己出的卡；不与执行共用会话 |
| **验收岗（AC）** | 读复核回执，独立抽查证据；对涉及财务计算的改动自己读 diff 并跑探针；决定"证据是否成立" | 不替 Owner 判断"这是不是想要的东西" |
| **Owner（项目验收）** | 最终决定：是否是想要的东西；所有设计、命名、文案的批准；冻结令；手机上看和点 | — |

**规划岗与复核岗是不同的会话。** 规划岗出的任务卡，由验收岗或 Owner 抽查，不由规划岗自己复核（Owner 2026-10-30 确认保留此条）。若复核岗与规划岗是同一个模型，也必须是两个独立会话，复核岗不得读取规划岗对该卡的"自评"。

## 2. 流转

```
PL 出任务卡（含验收标准、白名单、证据路径、停止条件）
  → AC 对卡做"可验收性"检查（见第 4 节）后放行
  → EX 执行，回执只能写 PENDING_AUDIT / BLOCKED / INCONCLUSIVE
  → RV 独立复核（单独会话）
  → AC 验收：读 RV 回执 + 抽查证据（财务类还要读 diff 并跑探针）
  → Owner 项目验收（涉及手机或设计的，由 Owner 在手机上看）
```

任何一步 FAIL：第一次，EX 按 RV 给的缺陷定点修复；**同一问题第二次有效失败，交回 PL 做根因分析**，不让 EX 盲目重试。BLOCKED（权限、手机锁屏、环境）不算失败，不累计。

## 3. 财务计算、数据库、两本账代码：C 路线与硬条件

Owner 选择：这类代码**可以由执行岗写**，但必须满足全部条件，缺一不可：

1. **范围：** 触及 `src/model/**`、`src/application/product-service.ts`、`monthly-model-service.ts`、`v2-expense-service.ts`、`migrations/**`、`repositories.ts` 的写路径，或 V1/V2 两本账同步的任务，一律属于此类。
2. **先有口径：** 任务卡里必须写明"改成什么行为"，并附**规格出处**（`FINANCIAL_MODEL_SPEC.md` 的章节）或 **Owner 已确认的口径原话**。没有口径的，不得出卡。口径由 PL 提案、Owner 确认。
3. **先写失败的测试：** 任务卡要求 EX 先写一个**在旧代码上会失败**的测试（变异验证），再改代码。M1 里每次修复都做过这一步，它是发现"测试其实没测到东西"的唯一办法。
4. **保护区哈希：** 修改前后，`src/model` 与 `migrations` 的聚合哈希必须在任务卡里**显式声明**会变还是不变。要变的，要在卡里写明变哪几个文件、为什么。
5. **验收岗必须自己读 diff 并跑探针。** 不能只看回执和门禁。探针是一个临时测试，用真实服务加内存库，复现任务卡所说的场景，输出具体数字，用完删除。M1 的现金不扣、未录债务、建议为 0 隐藏超支三个问题，全是这样发现的。
6. **Owner 的项目验收不可省**：这类改动改变的是数字，Owner 要在手机上看到数字并确认"对"。
7. **回滚：** 任务卡写明怎么回到改动前（基线提交哈希）。

## 4. 验收岗对任务卡的"可验收性"检查（出卡后、执行前）

放行前，验收岗只问五件事，任何一件答不上来就退回规划岗：
1. 验收标准是不是**可数、可复核**的？（"体验更好"不行，"打开记账弹层后 `document.activeElement` 是金额输入框"行。）
2. 有没有写**不做什么**？
3. 证据路径和停止条件有没有写？
4. 这张卡是不是**一件事**？
5. 财务类的，第 3 节七条是不是都在卡里？

## 6. 独立性与现场规则（吸取 T07 的教训）

- **同一时间只有一个会话在工作树里写。** T07 第一次复核停止，原因是我（当时的牵头）在复核启动的同一时刻还在提交文档。以后：任何会话开工前，先在 WORKLOG 写一行"开始"，结束时写一行"结束"；其他会话看到别人的"开始"没有"结束"，不动工作树。
- **复核岗读 WORKLOG 时，跳过规划岗和验收岗写的带结论的行。** WORKLOG 是只追加的，不能删。
- **执行岗、复核岗都不得改 WORKLOG 旧行。** T07 里发生过一次原地修改自己那一行的先例，已核实旧行没被动；以后写错了就**追加一行更正**，不用 `sed`。
- **手机库副本：** 一律取到 `/tmp` 读完即删，证据里只留哈希和文本读回。不要放进项目目录（会含 Owner 的昵称与金额）。
- **对手机只读：** 允许 `devicectl` 的 `list`、`info`、`copy from`；禁止 `install`、`uninstall`、`launch`、`terminate`、`copy to`。需要对手机写的，停下交给 Owner。
- **写类 git 命令只有验收岗或 Owner 可以执行**：`commit`、`add`、`reset`、`checkout`、`restore`、`clean`、`stash`、`rebase`、`merge`、`push`。执行岗和复核岗只读 git。

## 7. 与调度规则 V1.2 的对照

- 执行方自报完成不等于 PASS（§10.2）：EX 回执只能写 PENDING_AUDIT。
- 审核独立（§1.4、§10.2）：RV 是单独会话；PL 不复核自己的卡。
- 回执五态：PASS / FAIL / BLOCKED / PENDING_AUDIT / INCONCLUSIVE。
- 模型建议只给 Owner（§10.5）：本文件不含模型名。
