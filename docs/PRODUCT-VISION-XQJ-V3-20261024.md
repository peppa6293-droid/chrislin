## 1. 产品定位

### 1.1 已确认的定位

【已确认】小钱家 V3 的定位由三块拼成，缺一不可：

1. **主流记账软件的成熟功能与页面布局。**
   记账这件事本身不发明新范式：收入、支出、账户、分类、统计、导入导出等，按用户已经熟悉的成熟产品形态来做。用户不应为了用小钱家而重新学习一套记账逻辑。
2. **多邻国式的原创卡通角色、丰富表情和肢体动画。**
   借用的是「完成动作 → 即时反馈 → 愿意明天再来」的习惯机制，不是复制多邻国的品牌、角色、配色或文案。角色必须是**原创**的。
3. **长期财务预测、债务管理、现金安全作为核心差异化。**
   这三项是 V3 相对普通记账软件的真正差异点，也是产品存在的理由。记账是入口，预测与安全感是价值。

### 1.2 生活化命名原则

【已确认】页面及板块名称要生活化，不要财务术语堆砌（例如不要一上来就叫「资产负债表」「现金流折现」）。

【待决策】D1：各页面、板块、功能的最终名称。本文出现的名称（如「今天」「记录」「进展」「我的」「钱豆」）均为临时工作名，仅用于讨论，Owner 可整体改名。

【建议】命名遵循三条：说人话、不超过 4 个字、能在导航里并排放下；专业术语只出现在可展开的解释层。

### 1.3 与 V2 定位的关系

V2 文档（`docs/XIAOQIANJIA_PRODUCT_DESIGN_V2.md`）的定位是「每天花几秒钟照顾自己的钱」的轻量陪伴 App，并把长期预测、完整投资交易、0–100 健康分列为**明确不做**。

V3 保留 V2 的陪伴感与低维护原则，但把「长期财务预测」从「不做」提升为「核心差异化」。这是方向性变更，应当视为 **V3 对 V2 非目标清单的一次修订**，而不是 V2 执行走偏。

【待决策】D2：V3 是否正式废止 V2「明确不做」清单中与本文件冲突的条目（至少包括「24 个月预测」「复杂预算表」两项表述）。在 Owner 明确废止前，两份文档存在表述冲突，实现方遇到冲突时应以本文档为准并上报。

## 2. 日常记账

### 2.1 已确认的范围

【已确认】日常记账必须覆盖以下五类财务事件：

| 事件 | 说明（Owner 原话范围） |
| --- | --- |
| 收入 | 工资、兼职、报销、退款等资金流入 |
| 支出 | 日常消费、固定支出等资金流出 |
| 转账 | 账户之间、账本之间的资金移动 |
| 还款 | 信用卡、贷款等债务的偿还 |
| 资产维护 | 资产余额更新、资产买入/卖出/估值调整等维护动作 |

【已确认】三项体验要求：

1. **操作简单** —— 录入路径要短，不需要为了记一笔而填十个字段。
2. **分类完善** —— 分类体系要能覆盖真实生活，具体见第 3 章。
3. **快捷录入** —— 常用场景要能几秒内完成。

### 2.2 专属钱包与角色动画

【已确认】每一种财务事件都拥有**专属的钱包**和**专属的角色动画**。也就是说，「支出」不只是表单上换一个类型下拉，而是换成另一套视觉与动作：钱包形态、金币流向、钱豆的动作都不同。

【建议】五种事件对应五套「钱包 + 动作」组合，形成可记忆的视觉语言：

- 支出：金币从钱包飞出。
- 收入：金币落入钱包。
- 转账：金币在两个钱包之间移动。
- 还款：信用卡/欠条从钱包中被收走。
- 资产维护：钱包里的内容物变成金条。

【待决策】D3：转账与还款是否也各自需要独立的钱包形态，还是复用「支出钱包 + 不同图标」。这直接决定动画资产数量。

### 2.3 与现有能力的关系

【未验证】U1：现有 App 的记账主流程是否已覆盖「转账」「还款」「资产维护」三类事件的独立录入入口。已知现有实现以消费记账为主（`expense_records` / `expenses`），收入与资产、债务维护走的是「财务维护」类界面，是否满足 V3「五种事件平级、各有专属入口」的要求，尚未验证。

## 3. 分类与统计

### 3.1 分类体系

【已确认】支持**自定义一级、二级分类**（两级，不要求无限层级）。

【已确认】分类管理必须支持六种操作：

1. 新增
2. 修改
3. 排序
4. 隐藏
5. 合并
6. 归档

【建议】六种操作的语义建议如下，避免实现时各自理解：

| 操作 | 建议语义 | 对历史数据的影响 |
| --- | --- | --- |
| 新增 | 创建一级或二级分类 | 无 |
| 修改 | 改名、换图标/颜色、改所属一级分类 | 历史交易跟随新名称显示，金额归集不变 |
| 排序 | 调整展示顺序 | 无 |
| 隐藏 | 从录入选择器中移除，统计仍计入 | 历史不变，可恢复 |
| 合并 | A 分类并入 B 分类 | 历史交易改挂 B，A 归档 |
| 归档 | 停用但保留历史 | 历史仍可查，不再可选 |

【待决策】D4：**合并是否可撤销**。合并会改写历史交易的分类归属，属于高风险操作。是否要求「合并前预览影响笔数与金额」「合并后限时撤销」，需 Owner 决定。

【待决策】D5：**删除**是否需要。Owner 只提到「归档」，未提到硬删除。建议不提供分类硬删除，只提供归档。

### 3.2 统计周期

【已确认】统计支持五种周期：

- 近 1 个月
- 近 3 个月
- 近 6 个月
- 近 1 年
- 自定义周期（起止日期由用户指定）

【待决策】D6：「近 1 个月」的口径是「自然月」还是「滚动 30 天」。两者在月初/月末会给出不同数字，必须在实现前定死，并在界面上让用户看得出是哪一种。

### 3.3 同期比较

【已确认】支持「本月与上月同期」比较。即不是拿本月 1–24 日与上月整月比，而是与上月同一日期区间比。

【建议】同期比较必须同时显示绝对差额与百分比，并在分母过小时（例如上月同期仅 3 笔）弱化百分比、避免夸张的百分比数字。

【待决策】D7：当本月尚未结束、上月天数更少（例如 3 月 31 日对 2 月）时，同期区间如何截断。

### 3.4 分类分析

【已确认】消费分类需要支持四种分析视角：

1. **横向对比** —— 分类之间的绝对金额比较。
2. **趋势** —— 同一分类随时间的走向。
3. **占比** —— 各分类占总支出的比例。
4. **排行** —— 按金额排序的分类榜单。

### 3.5 逐层下钻

【已确认】支持四层下钻路径：

```
分类 → 子类 → 商家 → 交易
```

【建议】每一层都要能回答「上一层这个数字是怎么来的」，并且下钻后仍保留返回上一层的路径与当前筛选条件。

【待决策】D8：「商家」维度的来源。现有数据里商家信息主要来自导入账单的备注/对方名称，并非结构化字段。是否要新建商家主数据（含别名归并，例如「星巴克」「STARBUCKS」「星巴克咖啡」视为同一家），需 Owner 决定。

【未验证】U2：现有 App 的分类是**扁平结构**（数据库 `expense_categories` 表无父级字段、无排序字段），既不支持二级分类，也不支持排序/合并/归档。V3 的分类管理属于结构性新增，而非界面调整。

### 3.6 月度对比

【已确认】月度对比需覆盖四个维度：

1. 收入
2. 支出
3. 固定费用
4. 债务余额

【建议】四个维度各自独立呈现，不合成单一「财务健康分」。这一点沿用 V2 的既有原则：不使用跨量纲综合分。

## 4. 周期记账

### 4.1 已确认的范围

【已确认】周期记账覆盖的典型项目：房租、工资、车贷、保险、订阅。

【已确认】每条周期规则需要能设置：周期（频率）、金额、账户、起止时间、提醒设置。

【已确认】核心价值：**一次建立规则，后续自动进入未来财务模型**。用户不需要每个月手工重记一次。

### 4.2 预计与实际分离（关键规则）

【已确认】预计与实际必须分别管理，**不重复记账**。

【建议】建议采用以下模型，供 Owner 确认：

- 周期规则产生的是「预计发生」（planned occurrence），它是模型的输入，不是账本事实。
- 到了发生日，用户确认后，才生成一笔「实际交易」（actual transaction），进入账本。
- 预计与实际的关联通过规则 ID + 期次建立，同一期次只能有一次实际入账。
- 统计与账本只认真实交易；预测与现金安全线只认「预计 + 已实际」的合并视图。
- 任何情况下不得出现「规则生成了预计，用户又手工记了一笔，两边都算」的双计。

【待决策】D9：**自动入账 vs 确认入账**。工资这类确定性高的项目，是否允许「到期自动记为实际」；房租、订阅这类是否必须用户确认。建议按项目类型区分，但需 Owner 定。

### 4.3 四种操作

【已确认】周期规则必须支持四种操作：

1. **支付确认** —— 本期已发生，转为实际交易。
2. **跳过** —— 本期不发生，且不计入未来预测。
3. **暂停** —— 规则整体暂停，恢复后从下一个周期继续。
4. **金额调整** —— 本期或从本期起调整金额（例如房租涨价、订阅改套餐）。

【待决策】D10：「金额调整」的作用范围是「仅本期」还是「本期及以后」。建议提供两个选项并默认「本期及以后」，但需 Owner 确认。

【待决策】D11：「跳过」与「暂停」的差异是否需要在界面上明确解释。两者都能让本期不扣钱，用户容易混淆，是否需要合并为一个功能。

【未验证】U3：现有 App 没有周期记账规则的数据结构（无对应数据表、无规则引擎）。现有「经常性收入」只是从收入记录里推算出的展示值，不是规则。V3 的周期记账属于全新模块。

## 5. 每日提醒

### 5.1 已确认的范围

【已确认】提醒分两类场景：

1. **普通日常记账提醒** —— 提醒用户今天还没记账。
2. **事件型提醒** —— 在工资日、还款日、订阅续费日，用**替换过的文案**代替常规提醒，而不是继续发「今天记账了吗」。

【已确认】钱豆在这些提醒中要根据事件变化表情与动作（工资日开心、还款日紧张、续费日提醒）。

【已确认】提醒需要支持四种交互：

1. 提前提醒（事件发生前的预告）
2. 当天确认（当天完成确认）
3. 事后核对（错过之后补核对）
4. 提醒设置（开关、时间、频率）

### 5.2 建议的提醒分层

【建议】三层结构，避免提醒变成骚扰：

| 层级 | 触发 | 文案基调 | 频率上限 |
| --- | --- | --- | --- |
| 日常提醒 | 当天无记账且已过设定时间 | 轻松邀请，不指责 | 每天 1 次 |
| 事件提醒 | 工资/还款/订阅日前 N 天及当天 | 具体、可执行，带金额 | 每事件最多 2 次 |
| 事后核对 | 事件日已过但未确认 | 平静补账，不制造焦虑 | 每事件 1 次 |

【待决策】D12：**默认是否开启提醒**。记账类 App 的提醒默认开启容易造成反感，建议默认关闭、首次完成记账后询问一次。需 Owner 定。

【待决策】D13：提醒的**默认时间**（例如 21:00）与可选的提前天数（例如提前 1 天 / 3 天）。

【未验证】U4：现有 App 在桌面端是否具备系统级通知能力（含权限申请、通知点击后跳转、应用未运行时的提醒）。已知代码中存在「系统通知权限不可用则改为应用内提示」的降级逻辑，但完整的系统通知链路尚未验证。**这是 V3 提醒功能的前置技术条件，若不具备，需先补技术能力再谈交互设计。**

## 6. 多账本

> 本章是 V3 结构上最重的一块，也是风险最高的一块。规则必须写死，不能留给实现方临场发挥。

### 6.1 已确认的范围

【已确认】多账本的四条基本规则：

1. **每个账本独立记录和管理。**
2. **每本账本拥有自己的分类、预算、分析、周期规则和财务模型。**
3. **每本账本提供用户可自主勾选的「计入总账」开关。**
4. **未勾选的账本继续独立运行，但不参与总模型。**

【已确认】总模型必须**避免同一交易、账户、资产、债务被重复汇总**。

【已确认】支持**官方基础模板**和**高级自定义账本模板**。

### 6.2 「计入总账」规则（必须完整实现，不得简化）

以下为实现时必须满足的规则集：

| 编号 | 规则 | 说明 |
| --- | --- | --- |
| M1 | 开关粒度 | 「计入总账」是**每本账本一个**的开关，由用户自主勾选，不由系统按类型自动判定 |
| M2 | 默认值 | 新建账本时开关的默认状态需 Owner 定（见 D14）；模板可以预置建议值，但用户可改 |
| M3 | 关闭后的行为 | 账本**照常独立运行**：可记账、可统计、可预测、可看自己的模型；只是不进入总模型 |
| M4 | 关闭后的数据保留 | 关闭开关不删除、不迁移、不冻结任何历史数据；重新打开后总模型立即恢复纳入 |
| M5 | 历史口径 | 开关切换后，总模型按**当前开关状态 + 历史期间**重算，还是只对切换之后的期间生效，需 Owner 定（见 D15） |
| M6 | 总账去重 | 总模型汇总时，同一笔交易、同一个账户、同一项资产、同一笔债务，**在全库只能被计入一次** |
| M7 | 共享账户归属 | 一个真实银行账户被多个账本引用时，必须只有一个「归属账本」负责它的余额；其他账本只能引用其流水视图，不得各自再计一次余额（见 D16） |
| M8 | 转账不产生净资产变化 | 账本之间的转账，在总模型里是内部转移，不得计为收入或支出 |
| M9 | 债务不重复计 | 一笔贷款被账本 A 记为正债、账本 B 记为还款计划时，总模型只能认一份本金余额 |
| M10 | 汇总可解释 | 总模型的每个数字都必须能回答「由哪几本账本、哪些账户构成」，并提供下钻 |

### 6.3 建议的账本模板

【建议】模板解决「新建账本时一片空白」的问题，分两档：

**官方基础模板**（开箱即用，不要求用户理解财务模型）

- 个人日常
- 家庭共同
- 副业/经营
- 大额目标（如装修、旅行、购车）

**高级自定义模板**（面向愿意配置的用户）

- 可自定义分类树、预算规则、周期规则、是否计入总账、模型参数
- 可保存为模板供以后新建账本复用
- 可导出/导入模板

【待决策】D17：高级自定义模板是否属于 Pro 收费能力（与第 10 章联动）。

【待决策】D18：模板是否允许跨用户分享/导入（涉及模板文件格式与安全审核）。

### 6.4 典型使用场景（用于检验规则是否够用）

【建议】以下场景应在设计阶段就跑通，否则规则不完整：

1. 个人账本 + 家庭账本：家庭账本的共同支出计入总账，个人账本的个人消费也计入总账，两者不重叠。
2. 个人账本 + 副业账本：副业账本单独看盈亏，但副业收入最终进个人账户，总模型不能把「副业收入」和「转入个人账户的钱」各算一次收入。
3. 一本账本被关闭总账：用户想看「如果只看个人消费会怎样」，关闭家庭账本后总模型应立即变化。
4. 共享信用卡：夫妻各有一本账本，同一张信用卡的账单只能在一处计负债。

【未验证】U5：现有 App 是否具备多账本能力尚未验证。已知数据库迁移中没有账本表、也没有账本外键，记录直接挂在 `profile` 下，据此判断为「单账本 + 单用户」结构（该判断仍需盘点确认）。V3 的多账本（含每本独立分类、预算、模型、总账开关）属于数据模型级重构，不是加一个下拉框。

【风险提示】多账本与「总账去重」会触及现有财务模型与账本口径。任何实现都必须先解决 M6–M9 的归属规则，**在没有明确规则前不得开工**，否则后期返工成本远高于前期设计成本。

## 7. 财务模型

### 7.1 已确认的模型输出

【已确认】V3 财务模型需要给出七类结果：

1. **可安全使用资金** —— 用户今天/本月可以放心花掉多少。
2. **现金储备及预留额** —— 手里有多少钱、其中多少是必须留住的。
3. **资产与负债** —— 当前家底与欠款。
4. **长期现金流预测** —— 未来数月到数年的收支走向。
5. **债务还款进度、预计还清时间** —— 还要还多久、什么时候能还完。
6. **未来财务情景模拟** —— 改变某个变量（例如多还一点、少花一点、换工作）会怎样。
7. **各账本独立预测以及总模型汇总** —— 单本账本可独立预测，也能看合并后的总预测。

### 7.2 建议的呈现原则

【建议】沿用 V2 已确立的四条原则，V3 不得违背：

1. 结论先行：先给一句话结论，再给数字，公式收进可展开层。
2. 事实、参数、推导结果三者分离，推导结果不得写回成事实。
3. 计划收入与实际收入分离；预计与实际分离（与第 4 章一致）。
4. 不发明跨量纲综合分（不做 0–100 健康分）。

【建议】「可安全使用资金」这一项最容易造成误解，建议同时给出三个数：今天可花、本月剩余可花、以及这个数字背后的假设（例如「已扣除本月房租与还款」）。

【待决策】D19：「长期」的具体跨度。建议给 12 个月 / 24 个月 / 60 个月三档，默认 24 个月。需 Owner 定，因为跨度直接决定界面密度与模型复杂度。

【待决策】D20：情景模拟允许用户改哪些变量（收入、支出、还款额、利率、一次性大额？），以及是否允许保存情景。

【待决策】D21：预测的精度承诺。预测必须明确标注为「基于当前参数的推算」，不得呈现为确定结果。是否需要显示置信区间或「乐观/基准/保守」三档，需 Owner 定。

【未验证】U6：现有 App 已具备单账本的现金流、安全垫、债务、资产模型与「可安全使用资金」类输出（V2 体系）。但 V3 要求的**长期预测、还清时间、情景模拟、多账本独立预测**是否已具备，尚未验证。已知 V2 明确把「24 个月预测」列为不做，因此长期预测大概率属于新增。

## 8. 动画与养成

### 8.1 角色

【已确认】原创角色「钱豆」（临时名），需要具备：

1. 多种**面部表情**（开心、紧张、惊讶、满意、担心等）。
2. 多种**眼神**变化。
3. 多种**四肢动作**（挥手、走动、抱金币、捂脸等）。

【待决策】D22：「钱豆」是否为最终角色名；是否需要第二个角色（例如「钱豆的朋友」用于特定场景）。

### 8.2 已确认的动画事件

【已确认】以下动画事件必须实现：

| 事件 | 动画内容 |
| --- | --- |
| 消费 | 金币从钱包飞出 |
| 收入 | 金币落入钱包 |
| 债务新增 | 信用卡进入钱包 |
| 资产维护 | 钱包变成金条 |
| 还款 | 专属动画 |
| 储蓄 | 专属动画 |
| 退款 | 专属动画 |
| 转账 | 专属动画 |
| 月度总结 | 专属动画 |

【建议】每类动画配一套「起手 → 主体 → 收尾」三段式，时长控制在 600–1200ms，不阻塞下一次操作，并完整支持系统「减弱动效」设置（静态版本仍要有完成感）。

### 8.3 养成系统

【已确认】四个养成要素：每日打卡、连续天数、成就、任务进度。

【已确认·硬约束】**成功反馈必须基于真实业务结果。**

这一条是本章最重要的规则，意味着：

- 没有真实记账成功，不得播放「记账成功」动画。
- 没有真实完成还款确认，不得点亮还款成就。
- 连续天数只能由真实发生的记账日累计，不得由打开 App、点击按钮或观看动画累计。
- 成就不得用随机奖励、抽奖、虚拟货币等与财务事实脱钩的机制替代。
- 保存失败时必须显示失败，绝不能先播动画再说失败。

【建议】养成系统只做「记录真实行为的镜子」，不做「独立于财务事实的游戏」。这与 V2 的原则一致：streak、徽章、角色奖励不得置于财务核心之上。

【待决策】D23：连续天数中断后是否清零、是否允许「补记昨天的账」来续上连击。建议允许补记事实但不允许补记连击，避免为了连击而伪造日期。

【待决策】D24：成就的数量与档位（例如 10 个 / 30 个 / 50 个成就），以及成就解锁是否需要有仪式感的全屏动画。

【未验证】U7：现有 App 已有角色组件、完成反馈层与月度小结页（`DuoGuide`、`V2FeedbackStage`、`V2MonthSummary`、`SaveFeedback` 等），但角色是否达到「多种表情 + 眼神 + 四肢动作」的资产标准，以及九类动画是否齐备，尚未验证。已知 V2 设计明确要求「优先使用真正的 bitmap/vector asset，不用大量 CSS 拼脸作为最终品牌资产」，V3 应延续该要求。

## 9. 账单导入导出

### 9.1 导入

【已确认】需要支持的导入来源：CSV、Excel、PDF、截图。

【已确认】导入需要自动识别：交易、商家、金额、分类、账户。

【已确认】导入流程必须支持：

1. **去重** —— 同一笔交易重复导入不能变成两笔。
2. **冲突识别** —— 与已有记录金额/时间/商家不一致时提示。
3. **用户确认** —— 识别结果必须经用户确认后才写入。
4. **批次撤回** —— 一次导入作为一个批次，可以整批撤回。

【建议】导入采用固定四步：选择文件 → 识别预览（逐笔可改）→ 冲突与重复处理 → 确认写入。写入后保留批次号，支持「撤回这一批」。

【待决策】D25：**PDF 与截图导入是否纳入 V3 首版**。这两项依赖 OCR/解析能力，实现成本与不确定性远高于 CSV/Excel。建议首版只做 CSV/Excel，PDF 与截图放到后续（并与第 10 章的收费能力联动）。

【待决策】D26：去重的判定键（金额 + 日期 + 商家？还是允许用户自定义容差）。判太严会漏去重，判太松会吞掉真实的同额消费（例如每天同样金额的早餐）。

### 9.2 导出

【已确认】需要基础导出能力。

【已确认】定制报表与高级识别作为**潜在收费功能**（见第 10 章）。

【建议】基础导出至少包含：全量交易 CSV、按期间导出、以及一份可读的月度汇总。导出文件应带明确的时间范围与生成时间戳，避免用户手里的文件无法追溯。

【未验证】U8：现有 App 已有支付宝/微信 CSV 导入与「备份 JSON + 流水 CSV」导出，但 Excel、PDF、截图导入，以及批次撤回、冲突识别是否具备，尚未验证。已知导入侧有去重与确认步骤的痕迹，完整度需实测。

## 10. 商业化

### 10.1 已确认的边界

【已确认】免费版必须保障**基础记账能力**。也就是：一个用户即使永不付费，也能完整地记账、看分类统计、看月度对比。

【已确认】以下五项作为 Pro 的探索方向：

1. 高级多账本模型
2. 自定义模板
3. 长期预测
4. 自动识别（导入）
5. 高级分析

【已确认】当前**不确定最终定价，也不确定收费边界**。

### 10.2 建议的收费设计原则

【建议】五条原则，供后续定价时使用：

1. 免费版不设「记账条数上限」——限制记账次数会直接摧毁产品口碑。
2. 付费点放在「更远的未来」和「更省力的自动化」上，而不是「能不能记账」。
3. 已免费获得的数据能力不回收（例如用户已有的分类统计不因降级而消失）。
4. 试用期结束后的降级必须保留全部数据可读、可导出。
5. 不做「按账本数量阶梯收费」这类让用户不敢建账本的设计。

### 10.3 待决策清单

【待决策】D27：Pro 的具体权益清单（上述五项中哪几项进入 Pro，哪几项保持免费）。
【待决策】D28：定价模型（订阅制月/年、买断、还是「基础免费 + 高级订阅」混合）。
【待决策】D29：是否提供试用期，以及试用期长度。
【待决策】D30：付费渠道与合规（App Store 内购 vs 外部支付；这会直接影响 App Store 审核策略，必须在开发前定）。

【建议】商业化决策建议**晚于** V3 核心体验定型。在「值不值得付费」被验证之前定价格，容易定错。

## 11. Owner 逐项设计审批机制

> 本章为**强制治理规则**，不是建议。它与第 1–10 章的产品规划同级，且在执行顺序上**优先于**任何设计与开发动作：没有走完本章流程的设计，不得进入正式实施。

### 11.1 为什么需要这一章

V2 阶段的真实教训是：设计稿本身完成度不低，但户主第一次看到成品时才发现「界面是数字堆砌、看不懂、没反馈感」，于是整轮返工。根因不是设计能力不足，而是**审美判断权与业务判断权没有交回 Owner，而是被代持了**。

V3 的规则因此从「做完再评审」改为「**逐项提案、逐项确认、确认后才做**」。Agent 的职责是提出可比较的方案、做出可看的样片、按批准结果实现；**判断「好不好、对不对、像不像小钱家」的权力归 Owner**。

### 11.2 适用范围：什么必须逐项审批

【已确认】以下五类对象，**每一类都必须逐项获得 Owner 确认**，不得以「整体风格已定」为由批量通过：

| 类别 | 代码 | 必须逐项审批的内容 | 「逐项」的含义 |
| --- | --- | --- | --- |
| 界面与视觉 | A | UI 页面、组件、布局、配色、间距、字阶、圆角、图标、状态样式 | 一个页面算一项；同一页面的空态、加载态、错误态各自另算 |
| 命名 | B | 导航名称、板块名称、页面名称、功能名称、账本模板名称 | 每一个出现在界面上的名称都算一项 |
| 文案 | C | 首页欢迎语、每日问候、按钮文字、提示语、空状态文案、错误反馈、角色台词、Toast、表单校验提示 | 每一句用户可见的文字都算一项，含同一含义的不同场景变体 |
| 交互与动画 | D | 交互流程、转场、动效、角色表情、身体动作、动画节奏 | 表情、身体动作、转场、节奏**分别**接受反馈，不得打包成一个「动画已确认」 |
| 特殊提醒 | E | 日常记账提醒、工资日、信用卡还款日、会员续费日等场景的通知文案 | 每一个场景单独审批；同一场景的提前提醒/当天/事后核对文案分别审批 |

【已确认】动画类对象必须提供**可查看或可操作的样片**。只给文字描述、只给静态截图、只说「会做一个金币飞出的效果」都不构成可审批对象。

### 11.3 十条强制规则

【已确认】R1 —— **UI 页面、组件、布局、配色等必须由 Owner 逐项确认。**
落地含义：不存在「Agent 自行决定后通知 Owner」的路径。任何界面元素在进入实施前，都必须有一条对应的 APPROVED 记录。

【已确认】R2 —— **所有导航名称及板块名称最终由 Owner 决定。**
落地含义：Agent 可以提案、可以给候选清单和理由，但不能自行定名。本文第 1.2 节的「生活化命名原则」是方向，不是命名结果；第 14 章 D1 仍是未决项。

【已确认】R3 —— **首页欢迎语、每日问候、按钮、提示、空状态、错误反馈、角色台词等文案必须逐项审批。**
落地含义：文案与视觉同等对待。文案不是「实现时顺手写」，而是独立审核对象；同一按钮在不同状态下的文字（默认/悬停/禁用/进行中）也要分别列出。

【已确认】R4 —— **所有交互和动画需要提供可查看或操作的样片；角色表情、身体动作、转场和动画节奏分别接受反馈。**
落地含义：四类动画要素分开提审。Owner 可以批准「表情可以，但节奏太快」，此时表情 PASS、节奏进入 REVISION_REQUIRED，二者分别记录，不得因为一项通过而连带通过另一项。

【已确认】R5 —— **日常记账提醒、工资日、信用卡还款日、会员续费日等特殊提醒文案必须逐场景审批。**
落地含义：提醒文案是「最容易写错、最容易被用户每天看到」的文案，因此按场景拆到最细：工资日一条、还款日一条、续费日一条，各自的提前/当天/事后版本再拆。

【已确认】R6 —— **每次仅提交一个清晰的审核对象，附推荐方案和必要的替代方案。**
落地含义：一次提交只有一个对象、一个版本号。必须包含「我推荐哪个、为什么」以及「另外 1–2 个可行替代、各自代价」。只给一个方案等于把选择题变成判断题，不符合要求。

【已确认】R7 —— **未获 Owner 明确确认的设计不得进入正式实施。**
落地含义：没有 APPROVED 记录就没有代码。开发分支上出现未审批设计的实现，视为无效工作，不计入任何验收。

【已确认】R8 —— **不得以一次性整包评审代替逐页、逐项审核。**
落地含义：禁止「这是 V3 全套 32 个页面，请您整体看一下」这种提交。整包评审只能作为**进度同步**，不能作为**批准行为**；同步会上的「看起来不错」不产生 APPROVED 记录。

【已确认】R9 —— **每项审核必须记录版本、状态、Owner 意见和批准范围。**
落地含义：四要素缺一不可。其中「批准范围」最容易被省略，也最关键——必须写清「批准了什么、没批准什么」，例如「批准首页两卡布局与配色，未批准动效节奏与文案」。

【已确认】R10 —— **已批准设计不得由 Agent 擅自修改；新增变更重新进入审核流程。**
落地含义：APPROVED 即冻结。任何改动——哪怕只是「顺手把间距从 24 调到 20」——都必须升版本、写变更说明、重新提审。

### 11.4 审批状态机

【已确认】状态定义固定为六个，不得增删或改名：

```
DRAFT → OWNER_REVIEW → REVISION_REQUIRED / APPROVED → IMPLEMENTATION → VERIFIED
```

| 状态 | 含义 | 谁能进入 | 允许的下一步 |
| --- | --- | --- | --- |
| `DRAFT` | Agent 正在准备对象与样片，尚未提交 | Agent | `OWNER_REVIEW` |
| `OWNER_REVIEW` | 已提交，等待 Owner 判断 | Agent 提交后自动进入 | `REVISION_REQUIRED` / `APPROVED` |
| `REVISION_REQUIRED` | Owner 要求修改，附具体意见 | 仅 Owner | 回到 `DRAFT`（版本号 +1） |
| `APPROVED` | Owner 明确批准，批准范围已记录 | 仅 Owner | `IMPLEMENTATION` |
| `IMPLEMENTATION` | 正在按批准范围实现 | Agent | `VERIFIED` |
| `VERIFIED` | 实现完成且回读证据与批准范围一致 | 验证方 | 变更时回到 `DRAFT`（新版本） |

**状态机硬约束：**

1. 只有 Owner 能把 `OWNER_REVIEW` 推向 `APPROVED` 或 `REVISION_REQUIRED`。Agent 不得自批、不得代填 Owner 意见。
2. 不存在 `DRAFT → IMPLEMENTATION`、`OWNER_REVIEW → IMPLEMENTATION` 的捷径。跳过 `APPROVED` 即为违规。
3. `REVISION_REQUIRED` 必须带具体意见，不能只写「再改改」；无具体意见时视为无效驳回，Agent 应请求澄清而不是盲改。
4. `VERIFIED` 需要证据：实现结果与批准范围逐条对照的回读记录。没有对照记录的 `VERIFIED` 不成立。
5. `APPROVED` 与 `VERIFIED` 都是**版本绑定**的。版本号变化后，旧状态自动失效，必须重新走流程。

### 11.5 单对象提交规范

【已确认】每次提交必须是一个完整、自洽、可独立判断的审核包。审核包必须包含以下六项，缺任一项则该次提交无效：

| 序号 | 必含内容 | 说明 |
| --- | --- | --- |
| 1 | 审核编号与对象名 | 例如 `A-HOME-001 首页顶部区域` |
| 2 | 版本号 | 从 `v1` 起，每次修改递增 |
| 3 | 这一项要解决什么问题 | 一句话，避免 Owner 要先猜背景 |
| 4 | 推荐方案 + 理由 | 明确说「我推荐 B，因为……」 |
| 5 | 替代方案 1–2 个 + 取舍 | 各自代价，不只列好处 |
| 6 | 可查看/可操作样片 | 静态图、可交互原型、录屏或真机包；动效类必须可播放，含 reduced-motion 静态版 |

【建议】提交模板（可直接复用）：

```text
审核编号：A-HOME-001
对象：首页「今天」顶部区域（布局 + 配色，不含文案）
版本：v2（v1 意见：卡片过高、留白太多）
要解决的问题：用户打开 App 第一眼要知道「今天还剩多少能花」，现在要滚动才看得到。
推荐方案 B：两卡并排（结构余量 / 本月消费），回答"长期格局 + 短期进度"
  - 理由：一屏内同时回答长期与短期，符合第 7 章「结论先行」
  - 代价：窄窗口（<800px）需要改为上下堆叠
替代方案 A：单卡轮播
  - 好处：单卡信息密度高
  - 代价：需要用户滑动，第一眼只能看到一个维度
替代方案 C：四宫格
  - 好处：信息最全
  - 代价：回到 V2 被批评的"数字堆砌"，不建议
样片：交互原型（可点击切换两卡）+ 窄窗截图 + reduced-motion 静态版
请 Owner 决定：选 A / B / C，或指出具体不满意处
```

【建议】反例清单（出现任一项即应被退回）：

- 一次提交多个页面，或提交「全套设计」。
- 只给推荐方案，不给替代方案。
- 动效只给文字描述或单帧截图。
- 用「和 V2 保持一致」代替具体说明——V2 的设计本身正在被重新审视。
- 把文案混在布局里一起提，导致 Owner 无法单独评价文字。

### 11.6 审核记录格式

【已确认】每项审核必须记录四要素：**版本、状态、Owner 意见、批准范围**。

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| 审核编号 | 必填 | 全局唯一，建议 `类别-模块-序号`，如 `C-REMIND-003` |
| 对象 | 必填 | 精确到可识别，避免「首页」这种粒度 |
| 版本 | 必填 | `v1` / `v2` / …，每次修改递增 |
| 状态 | 必填 | 六状态之一 |
| 提交日期 | 必填 | Asia/Shanghai |
| Owner 意见 | 必填 | 原文记录，不改写、不概括 |
| 批准范围 | 必填（APPROVED 时） | 明确「批准了什么、没批准什么」 |
| 批准日期 | 必填（APPROVED 时） | 与 Owner 意见对应 |
| 实现证据 | 必填（VERIFIED 时） | 与批准范围逐条对照的回读记录 |

【建议】记录示例：

| 审核编号 | 对象 | 版本 | 状态 | Owner 意见 | 批准范围 |
| --- | --- | --- | --- | --- | --- |
| A-HOME-001 | 首页顶部两卡布局 | v2 | APPROVED | 「就 B，但两张卡高度要一样，别一高一低」 | 批准：两卡并排布局、等高的要求、配色；未批准：动效、文案、窄窗堆叠方式 |
| D-COIN-002 | 支出金币飞出动画 | v1 | REVISION_REQUIRED | 「太快了，看不清，慢一点，金币别飞太远」 | —（待 v2 重新提审） |

【待决策】D33：审核记录的存放位置与载体。建议在项目内建 `docs/design-approvals/`，一对象一文件，便于版本追溯与 diff；备选是在 App 内做一个审批面板（开发成本更高，但 Owner 操作更方便）。

### 11.7 什么算「明确确认」

【已确认·判定规则】只有以下情形算明确确认：

1. Owner 在审核记录中明确写出批准结论（含批准范围）。
2. Owner 以文字明确答复「这个可以」「按这个做」「B 方案通过」等含有明确同意意思的表述。

【已确认·判定规则】以下情形**一律不算**确认：

1. 沉默、未回复、超时未处理。
2. 问了但没答，或答了「再看看」「回头说」。
3. Agent 自行推断「没提意见就是没意见」。
4. 「你看着办」「你觉得好就行」——这类授权意味着**要求 Agent 重新提交更具体的选项**，而不是获得全权。
5. 会议口头「看起来不错」而无书面记录。
6. 工具侧的超时、关闭、取消（例如澄清请求未获回复），不得视为同意。

【建议】遇到 2 或 4 时，Agent 应把方案收敛到 2 个选项重新提交，而不是继续推进。

### 11.8 批准后的变更控制

【已确认】R10 的执行细则：

1. `APPROVED` 后，该版本内容冻结。冻结范围以「批准范围」字段为准，范围外部分仍可讨论。
2. 任何变更都必须：升版本 → 写变更说明（改了什么、为什么、影响哪些已批准项）→ 重新进入 `DRAFT` → `OWNER_REVIEW`。
3. 变更若波及已 `VERIFIED` 的实现，该实现的 `VERIFIED` 状态作废，需重新验证。
4. 旧版本的审核记录**保留不删**，形成可追溯链；不得用新记录覆盖旧记录。

【待决策】D34：是否允许「缺陷修复例外」——即不改变设计意图的纯缺陷修复（例如弹层被裁切、文字溢出、点击区域错位）可以先修复后报备，但须在 24 小时内补审核记录。建议允许，但限定为「不改布局、不改配色、不改文案、不改动效节奏」四不改。

## 15. 建议的推进顺序（非承诺）

【建议】以下只是降低风险的顺序建议，不构成排期承诺，也不代表已获批准：

1. **只读能力盘点**（U1–U10）→ 产出事实清单。
2. **规则定稿**（D2、D6、D8、D9、D14–D16、D19）→ 产出可实现的规则集。
3. **数据模型设计**（多账本、二级分类、周期规则、商家）→ 先设计后编码。

5. **多账本与总账去重** → 在单模块验证后再做，风险最高放后面。
6. **长期预测与情景模拟** → 依赖前面所有模块的数据基础。
7. **动画与养成** → 与功能并行，但必须等真实业务结果可被可靠判定之后再接反馈。
8. **导入导出扩展**（Excel → PDF/截图）。
9. **商业化** → 最后。
