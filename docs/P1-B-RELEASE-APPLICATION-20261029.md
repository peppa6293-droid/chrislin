## 2. 只读核实到的事实（本回合未访问活库，仅读代码与既有证据）

- **F1 首页现用规划收入**：`V2StructureCard.tsx:44` `income = home.planningIncome`；环心 `V2StructureRings.tsx:159-160` 显示该值；两环分母同源（`structure-ring.ts:structureRings`）。`planningIncome` 来自 `product-service.ts:439`，为模型输出，2026-10 生产首页显示 `¥13,000.00`（截图 `APP-HOME-2026-10-20261029-0000.png`）。
- **F2 实际收入有两本账，且写入入口不同**（这是本申请最关键的一条）：
  - `income_records(kind='ACTUAL')`：生产「记录本月收入」入口写这本（`financial-maintenance-service.ts:329 → repositories.saveIncome`），**收入页也读这本**（`MyFinancePages.tsx:531/599`，`actualIncomeRecords`）。2026-10 合计 **13,791.25**。
  - `income_entries`：只有 V2 记账服务写/读（`v2-expense-service.ts:319 recordIncomeEntry`、`:373 getDashboardProps`），生产收入入口不经此路径。Phase 1 为对齐双写了两表各 6 行。
  - 结论：**Q-1 建议的 `income_entries` 与生产「记收入」入口不是同一本账**。若首页读 `income_entries`，用户今后从生产入口记的收入不会出现在首页，会静默分叉；且首页与收入页两市。建议改读 `income_records`（与收入页同源）。
- **F3 首页状态里没有实际收入合计**：`HomeApplicationState`（`product-service.ts:51-124`）只有 `actualIncomeRecordCount`，无金额合计。故最小改动＝在该读取态加一个派生字段（见 §3），不新增 SQL——`built.input.facts.actualIncomeRecords` 已在内存中。
- **F4 双计风险点**：`PHASE1-READINESS.md §5` 已实测「同月三个收入数互不连通」，任何视图同时汇总两表 → 2026-10 显示 27,582.50。本申请的实现**只允许单表求和**，测试须含该反例（断言不出现 27,582.50）。
- **F5 现网既有可复用件**：`structure-ring.ts` 已在段 2 落地（`ringDatum/percentOf/structureRings`，`available/percent/overAmount` 已能表达不可算态与超额）；A 标记已在产品侧实现（`V2StructureRings.tsx:180-190`，3×14px / 圆角 2px / `#C2503C` / `aria-hidden` / 金额左侧 8px）。**P1-b 不需要动圆环绘制逻辑**，只换输入值。
