## 3. 完整模板规范（`EXISTING_VERIFIED`，逐项来自 `src/model/v2-import.ts`）

### 3.1 两套定死模板（列名必须逐字匹配）

| | 支付宝模板 `ALIPAY_CSV` | 微信模板 `WECHAT_CSV` |
|---|---|---|
| 必填列（逐字） | `交易号` `交易时间` `交易对方` `金额` `收支` `备注` | `交易单号` `交易时间` `交易对方` `金额(元)` `收/支` `备注` |
| 列顺序 | 不要求（按列名取值） | 不要求 |
| **额外列** | **不允许**：出现任何模板外列名，每一行都记 `Unknown columns` 异常（`:136-138`） | 同左 |
| 列数 | 每行字段数必须等于表头列数 | 同左 |

平台可由表头自动识别（`import-rules.ts:241` `detectImportProvider`），识别不了则退回界面单选。

### 3.2 字段格式要求

| 字段 | 要求 | 违反后果 |
|---|---|---|
| 编码 | **仅 UTF-8**（`File.text()`，`v2-import.tsx:180`）；无 BOM/GB18030 处理 | 中文乱码 → 表头不匹配 → 整文件失败 |
| 分隔符 | 半角逗号；支持双引号包裹与 `""` 转义（`parseCsvLine`） | — |
| 交易时间 | **必须带时区的 ISO 8601**：`YYYY-MM-DDTHH:MM:SS±HH:MM` 或 `…Z`（`:26-27`） | 真实账单的 `2026-10-21 14:08:38` **直接判非法**（已实测） |
| 金额 | 非负十进制、最多 2 位小数、可带 `¥` 前缀；上限 999999999999.99 | 负数（退款）判非法 |
| 收支 | 必须精确等于 `支出` 或 `收入` | 其他值（如 `不计收支`、`不计收支`）→ `UNKNOWN` 异常 |
| 备注 | 列必须存在（值可空） | 缺列异常 |
| 文件大小 | **无限制**（整文件读入内存字符串） | 大文件可能卡死，无提示 |
| 多文件/多页 | 不支持，一次一个文件 | — |

### 3.3 与真实账单的差距（这是本次最关键的实测）

户主真实账单在 `~/Desktop/林特/10.21导入账单/`（本次只读核对格式），本地解析脚本 `data/consumption-exports-20261021/parse_alipay.py` / `parse_wechat.py` 记录了真实格式：

| 真实来源 | 真实形态 | 当前 App 能否直接导入 |
|---|---|---|
| 支付宝导出 CSV | **GB18030 编码**；表头前有多行说明文字；11 列（`交易时间,分类,交易对方,对方账号,商品说明,收支,金额,收/付款方式,交易状态,交易单号,商家订单号`）；时间为 `YYYY-MM-DD HH:MM:SS` | **不能**（编码、表头偏移、列名、多余列、日期格式，五重不兼容） |
| 微信支付账单 | **XLSX**（不是 CSV） | **不能**（文件类型就不对） |
| 银行流水 PDF | 文字/扫描 PDF | **不能** |
| 支付截图 JPG | 图片 | **不能** |

实测证据（`evidence/import-audit-20261024/verify-import-audit.test.ts`，6/6 通过）：真实支付宝表头 → 判 missing columns 整文件失败；GB 字节按 UTF-8 解 → 乱码失败；真实日期格式 → `Invalid transaction time`。**换言之：现有导入器只能吃「先离线转好格式的 CSV」**，这正是 R12 当时不得不先写转换脚本（`r12_convert.py`）再走界面的原因。

## 4. 自动分类机制（`EXISTING_VERIFIED`）

- 规则表：10 组商家/摘要关键词（餐饮、出行、购物、日用、娱乐、居住、水电通讯、保险、医疗、教育），置信度 0.85–0.95，阈值 0.8（`LOW_CONFIDENCE_THRESHOLD`）。
- 命中方式：文本归一化后子串匹配，**最长关键词优先**（`import-rules.ts:192-198`）；同组内别名先精确后模糊映射到**用户自己的分类名**。
- 置信度呈现：界面用人话（「按『外卖』建议 · 95%」「不太确定…等你确认」「没匹配到规则，先用默认分类」），不要求用户理解技术评分（`v2-import.tsx:97-104`）——符合第五章要求的方向。
- 账户建议：仅 3 条提示（支付宝/微信/银行卡→按账户名模糊找），无学习能力。
- 局限（`PROPOSED` 前必须知道的）：规则覆盖约 70 个关键词，无用户自定义规则、无商家主数据/别名归并（产品愿景 D8 亦未决）、无从历史纠错中学习；真实账单里大量商户（如 `luckincoffee` 英文、`天**` 脱敏名）匹配不到，会全落默认分类——这与户主 2026-10-23 反馈的「分类全『其他』」现象同源。

测试证据：`tests/v2-ledger/import-rules.test.ts`（6 条，含阈值边界、无匹配返回 null、账户建议、平台识别）。

## 7. 多格式导入技术架构（`PROPOSED`）

### 7.1 适配管线

```
文件识别 → 解析/OCR → 字段映射 → 统一交易结构 → 分类及去重 → 用户确认 → 写入财务记录 → 计算模型更新
```

各段落的可复用/须新增（对照见 §8）：

1. **文件识别**（新增）：魔数+扩展名+编码嗅探（UTF-8/BOM/GB18030）→ 得到 `DetectedSource { kind, encoding, confidence }`。平台识别可扩展现有 `detectImportProvider`。
2. **解析/OCR**（新增适配器，接口统一）：每个格式一个 `SourceAdapter → RawRow[]`。CSV/TXT/XLSX 走纯代码解析；PDF/截图走 OCR 适配器（见 §7.3）。
3. **字段映射**（新增）：`RawRow → 规范交易`。内置已知模板映射表（支付宝/微信/主流银行），未知模板走**映射向导**（拖拽列名对齐 + 预览 20 行）。
4. **统一交易结构**（扩展现有）：在 `ImportedExpenseCandidate` 上加 `txnType: CONSUMPTION|INCOME|TRANSFER|REFUND|REPAYMENT|INSTALLMENT|FEE`、`counterparty`、`orderNo`、`status`、`rawSource`。**关键是先定性质再入账**——R2/R3 的根治点。
5. **分类及去重**（扩展现有）：分类继续用本地规则；去重升级为「同渠道单号精确去重（现有）+ 跨渠道指纹去重（金额±时间窗±对方）+ 退款配对（原单号）」。
6. **用户确认**（扩展现有预览）：见 §8 章第六节方案。
7. **写入**（复用）：`writeImportBatchAtomically` 事务+读回校验原样可用；补一张「交易性质」字段与转账/还款专用表。
8. **模型更新**（复用）：月度模型读 `expense_records` 的既有链路不动；只修 R5 的分类口径。

### 7.2 兼容性矩阵

| 格式 | 解析难度 | 建议阶段 | 技术选型建议 | 备注 |
|---|---|---|---|---|
| CSV（UTF-8/GB18030，含支付宝真实格式） | 低 | 阶段 1 | 现有解析器 + 编码嗅探 + 列映射 | 最高性价比 |
| TXT 表格（TSV/固定分隔） | 低 | 阶段 1 | 同上，分隔符可配 | |
| XLSX（微信官方账单） | 低-中 | 阶段 1 | 前端解析库（SheetJS 一类）或 Rust 侧解析 | 微信唯一官方出口，必做 |
| XLS（老格式） | 中 | 阶段 2 | 转 XLSX 或专用库 | 需求量小 |
| 文字型 PDF（银行流水） | 中 | 阶段 2 | PDF 文本抽取 + 表格重建 + 列映射 | 表格线断裂是难点 |
| 扫描型 PDF | 高 | 阶段 3 | 逐页渲染 → OCR | 见 §7.3 |
| PNG/JPG/HEIC 支付截图 | 中-高 | 阶段 2–3 | 本地 OCR + 模板抽取 | 截图版式固定，比流水 PDF 好做 |
| 多页账单 | 中 | 阶段 2 | 适配器内分页聚合 | |
| 多文件批量 | 低 | 阶段 1 | UI 改多选 + 合并预览 | 便宜 |
| 银行专用格式（如招行/工行 App 导出、云闪付） | 各异 | 阶段 2+ | 每家一个映射表 | 优先级由户主按实际账户定 |

### 7.3 本地 OCR 与截图识别可行性（`UNVERIFIED`，需小样本试点）

- **推荐路径：macOS 系统自带 Vision 框架**（经 Tauri 调系统能力）。特点：完全本地、免费、中文识别质量好、原生支持 PNG/JPG/**HEIC**，与 App「本地记录、不上传」的承诺一致。
- 备选：开源 OCR（Tesseract 一类）中文效果明显更差且要额外打包；云端 OCR 识别率高但**违背本地隐私承诺**，若考虑必须先过户主决策。
- 支付截图（微信/支付宝成功页）版式高度固定，成功率应显著高于任意流水 PDF——建议**先做截图、后做扫描 PDF**。
- 扫描 PDF = 逐页渲染成图再 OCR，成本最高，排最后。
- **风险声明**：OCR 准确率对截图清晰度、字体、遮挡敏感；金额与日期是财务关键字段，OCR 结果**一律进人工确认队列**，不得直入账（见 §8）。本条全部为 `UNVERIFIED`，立项前须用户主真实截图做 20–50 张小样本试点再定阈值。

## 8. 最简用户确认机制（`PROPOSED`）

原则：**普通交易整批过，只有影响四大基本盘的才拦下来。**

1. **两通道确认**
   - 通道 A（批量）：识别为 `CONSUMPTION` 且高置信、非重复、金额在常规区间的行 → 汇总成一行摘要（「另有 213 笔日常消费共 ¥8,432，分类置信度高」）+ 可展开清单，**一次勾选确认**，不逐条审。
   - 通道 B（必核队列）：仅以下 6 类进队列，逐条核对——
     ① 账户归属不明/跨账户；② 疑似影响真实余额或债务的记录；③ 疑似重复（含跨渠道）；④ 交易性质不明（转账？还款？消费？）；⑤ 退款/分期；⑥ 超过阈值的大额一次性支出。
2. **未确认不入账**：现有代码已保证只有 `CONFIRMED` 才写（`confirmImportBatch` + `writeConfirmedImport:126`），该不变式保留到所有新格式。
3. **置信度呈现**：沿用现有人话文案（「按『外卖』建议」「不太确定」），不出现技术分。
4. **批次可撤**：写入后保留批次号，提供「撤回这一批」（产品愿景 §9.1 已确认要求）。
5. **余额与债务永不被导入默认改动**：导入默认只记流水；要动真实余额/债务，必须走单独的「余额基准核对 + 一致性检查」流程（对应户主既定的修订表口径）。

## 9. 新用户快速初始化（`PROPOSED`，基于历史账单能恢复什么）

| 目标 | 能否由历史账单可靠算出 | 说明 |
|---|---|---|
| 历史消费及分类统计 | **能**（需先解决 R1 格式问题） | 有了流水即可按月/分类聚合 |
| 月度预算建议 | **能**（近似） | 用近 3–6 个月可变支出均值做起点；须剔除一次性大额（R9） |
| 周期固定支出候选 | **能**（需新增分析） | 按「同商户/同金额/按月重复」自动提名（房租、话费、订阅…），用户一键采纳 |
| 收入历史 | **不能**（现状） | 收入被丢弃（R6）；修掉后可恢复历史收入，但**稳定月收入仍需用户确认** |
| 已知现金账户与待核对余额 | **部分** | 账单里能发现「支付宝/微信/某银行卡」这些账户存在；**余额必须用户填**——账单是流水不是余额 |
| 信用卡账单与债务资料 | **部分** | 能发现卡号尾数与消费额；**本金余额/费率/期数必须用户填** |
| 抗风险计算 | **不能** | 安全目标、可动用储备、必要支出划分都依赖用户当期状态 |

**最短路径设计**：一次导入 → 自动给出「消费史 + 预算建议 + 固定支出候选 + 账户清单」→ 只追问 4 样：当前现金余额、稳定月收入、债务余额、安全目标。填完即出首份有依据的财务分析。历史账单负责「过去」，用户只补「现在」。

## 10. 可复用 vs 必须新增（对照表）

| 环节 | 可复用（`EXISTING_VERIFIED`） | 必须新增（`PROPOSED`） |
|---|---|---|
| 解析核心 | `parseCsvLine`、金额/日期校验、`parseImportFile` 骨架 | 编码嗅探、表头偏移跳过、列映射向导、XLSX/PDF/OCR 适配器 |
| 交易结构 | `ImportedExpenseCandidate`、`dedupeKey` 思路 | `txnType` 等性质字段、原单号/状态/对方字段 |
| 去重 | 唯一索引 `expenses_dedupe_unique`、批次内 Set 去重 | 跨渠道指纹去重、退款配对 |
| 分类 | `import-rules.ts` 规则表 + 置信度 + 人话文案 | 用户自定义规则、商家别名、从纠错中学习 |
| 确认流 | 预览列表、批量确认、`CONFIRMED` 不变式 | 行级排除勾选、必核队列两通道、批次撤回 |
| 写入 | `writeImportBatchAtomically` 事务+读回校验、`import_batches` | 转账/还款专用落账、收入写入、分类口径修复（R5） |
| 模型 | 月度模型读 `expense_records` 链路 | 一次性大额豁免、固定支出候选分析 |
| 导入历史 | `import_batches` 表（有数据） | 查看/撤回界面 |

**明确不要做的**（本次评估不主张）：全格式一次上齐、云端 OCR、自动动余额/债务、默认绕过确认写入。

## 11. 分阶段实施顺序、测试门槛与剩余风险

| 阶段 | 内容 | 测试门槛（不过不进下一阶段） |
|---|---|---|
| **P0 正确性止血**（最小可用） | R2 转账/还款识别与拦截、R3 退款配对、R4 跨渠道去重、R5 分类口径修复 | 新增性质识别测试集 ≥ 30 条真实形态样本；双渠道重复导入只留一笔；导入行在月度模型分类统计中不再全落「其他」 |
| **P1 真实格式** | 编码嗅探 + 列映射 + 支付宝真实 CSV/XLSX 直导 + 多文件批量 | 户主真实支付宝 CSV、微信 XLSX 各 1 份**原文件直导**成功，行数与金额对得上源文件；错误行可定位 |
| **P2 确认与初始化** | 必核队列两通道、批次撤回、导入历史界面、固定支出候选、新用户四问 | 撤回一批后库内无残留；未确认行 0 入账；新用户只填 4 项出首份分析 |
| **P3 图片与扫描** | 支付截图 OCR → 扫描 PDF | 20–50 张真实截图试点达约定准确率才量产；OCR 金额/日期 100% 进人工确认 |

**剩余风险（即使全做完仍在）**：OCR 准确率天花板；平台改版导致模板映射失效（需要映射向导兜底）；商家脱敏名（`天**`）导致分类上限；跨人共享账户/信用卡的归属判断（产品愿景 §8 已列）；大额一次性支出的「什么算一次性」需户主裁决口径。
