# EXEC-R11B 恢复与应用内重播任务书（交执行者）

发布者：审核员 ｜ 发布日期：2026-10-22 ｜ 执行者：**执行员**（非审核员本人）
性质：R11 直接 SQL 写库触发启动门闸 `PRODUCTION_INTEGRITY_STATE_CONTENT_MISMATCH` 后的收口方案。**裁决已定：不用写入前备份之外的任何旁路；先恢复 App 可用性，再用应用自己的界面重播真数。**

---

## 0. 裁决（审核员 2026-10-22，针对执行员 R11_BLOCKED 二选一的答复）

执行员问：「用写入前备份恢复 App 可用性，还是保留数据、另找一条启动校验认可的写入路径。」

**答复：恢复（方案一），并把写入版库留档后再恢复。理由：**

1. **「启动校验认可的写入路径」在直插 SQL 这条路上不存在。** 门禁机制（`src-tauri/src/lib.rs`）是：库里存内容指纹 + 用 terminal 内的钥匙盖的封条；启动先核对指纹与库内容一致，应用自身的写路径在写入时自动盖新指纹。直接 SQL 改库后指纹必过期，启动必拒。想绕过只有「拿钥匙手改完整性状态」一条路——违反红线（不动完整性状态 / terminal / receipt / permit），等同拆掉防篡改设计，验收叙事（验证应用链路）也会作废。**不采纳。**
2. **应用自身的写路径就是唯一正路**，而且它的写通道是通用 SQL 命令 + 事务（`database_execute` / commit 时盖指纹）——所以凡界面能录入的数据，都能合规进库。
3. 本次写入的数据**不丢**：值全部可从任务书 §1 确定性复现，且恢复前先留档一份完整副本。
4. App 打不开是 P0（真实包可打开是验收标准第一条），不能带着砖化的 App 讨论数据问题。

**由此拆出三步**：R11B-1 留档+恢复（本任务书 §3）、R11B-2 应用内重播界面可达部分（§4）、R11B-3 界面无入口的三组如实挂账为产品缺口 F5–F7（§6，禁止旁路写库凑数）。
