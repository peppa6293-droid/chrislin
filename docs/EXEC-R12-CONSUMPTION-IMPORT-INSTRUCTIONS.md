## 2. 转换契约（CSV 生成规则）

1. **每个 CSV 只含一个平台 × 一个 App 分类**（导入界面的默认分类/账户是整批统一的，不分批就会把整文件灌成同一分类）。产出 **12 个文件**，命名 `r12-alipay-餐饮.csv` 这般（平台-分类）。
2. **列名严格照抄（多一列少一列都会报 ERROR）**：
   - 支付宝 CSV 表头：`交易号,交易时间,交易对方,金额,收支,备注`
   - 微信 CSV 表头：`交易单号,交易时间,交易对方,金额(元),收/支,备注`
3. 字段取值：
   - 交易号/交易单号 = `order_no`
   - 交易时间 = `time` 转 ISO 8601 **带时区**：`2026-10-21 14:08:38` → `2026-10-21T14:08:38+08:00`（不带 T 或时区会被整行判 ERROR）
   - 交易对方 = `counterparty`（为空则取 `goods`；再为空则整行跳过并进对照表——实测纳入集内 0 行为空，属防御规则）
   - 金额/金额(元) = `amount` 原样（不带 ¥、不带千分位、不带正负号）
   - 收支/收/支 = `支出`
   - 备注 = `goods`
4. 编码 **UTF-8 无 BOM**；标准 CSV 引号转义（字段内含逗号/引号/换行须双引号包裹，`"` 写成 `""`）——商品说明里逗号极多，引号错了整批解析会乱。
5. 转换脚本放 `data/consumption-exports-20261021/`（与解析脚本同级），**不进 `src/`**。

## 4. 导入程序（只走 App 界面）

**前置**：①R11 真数重播已完成（否则「微信零钱」账户不存在，微信批次无账户可选）；②落地验收已收尾（或户主明确要求提前并已与审核员对齐）；③12 个 CSV + 对照表已生成且与 §3 锚点逐行一致。

1. 按 bundle id 启动 `/Applications/Personal Finance Console.app`（**不改包、不重建**）。
2. 进「账单导入」，**每批**：选对应平台（支付宝批选支付宝、微信批选微信）→ 选 CSV → 默认分类选该批分类 → 默认账户：**统一选「现金」**（**2026-10-22 审核员裁决**：导入界面的账户下拉只读 V2 `accounts` 表，生产库该表仅「现金」一个账户；「余额宝/微信零钱」只在旧现金账户表里，V2 账户无管理界面、选不到，见剩余问题 F8。原「支付宝批→余额宝、微信批→微信零钱」作废。账户字段不进现金快照模型，不影响资产与「已花」读数，真实付款方式留对照表可查）→ 确认预览 → 确认导入。共 **12 批**。
3. 每批记录界面回执的 `writtenRows / skippedRows / errorRows`，与 §3 该批行数比对。**任何一批 errorRows>0 或行数不符：停下保留现场报告**（界面不给行级错误，见 §7/B4，此时以对照表+SQL 自查，不许改数硬导）。
4. 导入是**永久的**（App 无删除入口）——预览阶段发现批量错分，先回转换层重生成 CSV，别急着点确认。

## 7. 已知限制（如实带进回执，不属失败）

1. **kind 恒为现金支出**：导入服务把每行落成 `CASH_DEBIT`，花呗/信用卡支付的消费也按现金支出入账（App 导入路径不支持信用消费）。对「已花/日常支出」总额无影响（照样是消费额），但「从哪个账户出」失真——见 2。
2. **账户归属粗粒度且统一为「现金」**（2026-10-22 裁决后）：V2 账户表仅「现金」一个账户且无管理入口（F8），12 批全部落「现金」。账户字段不进现金快照模型（余额由快照定，不由流水倒推），故不影响资产读数；逐行真实付款方式（花呗/招行信用卡/零钱…）留在对照表与源 JSONL。
3. **商品说明/付款方式不进应用内流水**：应用 description 只留交易对方；goods 写进 CSV 备注列供预览，落库后以对照表留档。
4. **分类永久**：无编辑/删除入口（剩余问题 B1/B3），导入前分类汇总必须人工过目。
5. **界面无行级错误**（B4）：只显示失败条数，故 §4.3 规定任何不符即停。
6. **部分退款不冲减**：微信「已退款(¥xx)」的消费行整行排除（宁少勿错）；支付宝全额退款已按 §1.2 #5 关联剔除。
